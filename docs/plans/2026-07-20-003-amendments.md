# Combat Engine Foundation — execution amendments

Decisions taken during execution that **supersede** parts of
`2026-07-20-003-refactor-combat-engine-foundation-plan.md`. The plan body is a
decision artifact and is not edited during execution; this file records where
reality diverged from it and why.

---

## A1 — Combatants carry their constructed equipment; the engine holds no weapon table

**Supersedes** KTD-3's `equipment_stats: (handle) -> Mapping[str, int]`, §2.2c's
"equipment lookup raises on an unknown handle", and every mention of
`weapon_stats` as a table passed alongside the fight (plan `:206`, `:303`,
`:573`, `:1137`, `:1244`).

**Status** Adopted during U2. **Decided by** the user, 2026-07-21.

### What the plan assumed

A fight receives `weapon_stats` — a `{weapon_id: stats}` mapping — and the rules
bundle receives an `equipment_stats(handle)` callable over it. A combatant
carries an opaque `equipment` *handle* (a weapon id); the engine resolves that
handle through the table when it needs stats.

### Why that is wrong

It creates **two sources for one fact**, and they can disagree silently.

Reproduced on the U2 working tree before this amendment:

```
fight = build_fight(..., weapon_stats={7: (99, 99, 20)}, rules=rules_for(WEAPON_STATS))
fight.weapon_range(7)      -> 20          # read from the fight's own table
fight.equipment_stats(7)   -> {ts: 6, tg: 15}   # read from the BUNDLE's table
```

The fight fires with stock accuracy/damage while its range comes from the custom
table. Nothing raises; the fight simply uses the wrong numbers. `tests/helpers.py`
avoided it by threading `rules_for(table)` at the call site — a **convention**,
not an enforced invariant, and one forgetful call site from recurring.

This is the same defect class as U1's stale weapon-stats copy and the vacuous
tests behind #49: **a wrong value that produces a plausible result instead of an
error.** Options that keep two lookups (validate they agree; prefer one over the
other) manage the symptom. Removing the second source removes the defect.

### The rule now

**The roster handed to combat is already fully constructed. The engine reads no
equipment data from outside it.**

- Each combatant carries its **weapon object**, not a weapon id — the object
  already holds its own stats (`ts`, `tg`, `range`, and whatever else the game
  put there).
- `CombatFight` takes **no** `weapon_stats` argument and holds no table.
- `RulesBundle` carries **no** `equipment_stats` callable. A formula reads the
  stats off the combatant's own equipment.
- Building the weapon object from config data is the **game's** job, done before
  the fight starts (the handlers already load `weapons.yaml`).

Consequences that fall out for free:

- The "unknown handle" failure mode **ceases to exist** — there is no handle and
  no lookup, so §2.2c's "raise on unknown handle" requirement is satisfied by
  construction rather than by a guard. The `(0, 0)` silent-default defect
  (plan `:303`) is likewise gone.
- U5's "inventing entities needs no new machinery" (`:1137`) gets *simpler*: a
  scenario builds a combatant holding whatever weapon object it likes. No
  parallel stats entry to keep in sync.
- The engine's attribute-agnosticism improves — it stops knowing that equipment
  is keyed by an integer id at all.

### Migration note

`weapon_stats` appears on `StartCombat` (`interactions.py`) and is threaded by
all three handlers. Those handlers already load the weapon table; they now
construct the weapon object onto each combatant instead of passing the table
alongside. `weapon_range`/`weapon_stats`/`equipment_stats` on `CombatFight` all
collapse into reading the combatant's own equipment.

This lands **inside U2** rather than as a follow-up: U2 is the unit that
introduces `RulesBundle` and `equipment_stats`, and shipping them only to remove
them one unit later would mean migrating every call site twice.

## A2 — `_effect_to_dict` walks with `json_safe`, not `dataclasses.asdict`

**Supersedes** nothing in the plan; this is a defect found during U2.

**Status** Adopted during U2.

Since U2 a nested `Fighter` carries an `attrs` mapping held as a read-only
`mappingproxy`. `dataclasses.asdict` deepcopies internally and `mappingproxy` is
not picklable, so it **cannot walk the frozen graph at all**:

```
dataclasses.asdict(Fighter(name="x", weapon=1, energie=10))
-> TypeError: cannot pickle 'mappingproxy' object
```

`engine/state/json_safe` is the engine's declared inverse of the frozen form and
unwraps it correctly, so `_effect_to_dict` uses that instead. This is the
serialization path the plan flags at `:880` as the one that broke in `9df2091` —
the same site, a second way to break it.

**Required follow-on:** `json_safe` has no return annotation, so a type checker
cannot see that `{**json_safe(effect)}` unpacks a mapping. Annotate it rather
than suppressing the four resulting errors in `persistence.py`.

## A3 — The terminal panel reads `attrs`; the theme names the fields

**Supersedes** U2's recommended option ("the panel flattens `attrs` back onto the
payload so the wire contract is unchanged").

**Status** Adopted during U2. **Decided by** the user, 2026-07-21.

The plan offered two options and recommended the compatibility one. The user
chose the optimal one: the presentation layer stops knowing this game's German
stat names.

Note the failure mode this avoids is **quieter** than the plan states. The plan
says the panel "silently renders blanks"; in fact `renderers.py` reads the stats
via `.get(name, 0)`, so it renders **zeros** — a plausible-looking fighter panel
showing 0/0/0. The plan's grep guard cannot catch it either way, because it only
scans `engine/`.

**Required:** assert the rendered panel is byte-identical before and after.
